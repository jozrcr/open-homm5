# Plan: a decompilation that runs by itself

Status: approved by the owner on 2026-10-24 (Q7): this PC, overnight and during the owner's work hours, up to ~90% of the subscription; batch PRs; the compiler from archive.org for CI; the code our mods touch first.

## In short

- **Goal:** rebuild the game's code as C++ source, function by function. Each function is proven byte-for-byte identical to the original by the oracle (`tools/verify/`). This is the long road to an open Heroes V engine, like VCMI for Heroes III.
- **Size:**
  - about **48,600 game functions** to do. Half of them are tiny (64 bytes or less). About 2,000 library functions stay out, and 16,800 functions the compiler generated mostly come along with the code around them.
  - **Done: 13** (the game timer, phase 0).
- **The idea:** a loop of AI agents.
  1. Each takes the next function of a source file and writes C++.
  2. It compiles it with the game's original compiler (Visual C++ 2003).
  3. It keeps it only if the oracle says the bytes match.
  4. Every batch becomes a pull request.
  5. GitHub re-checks every matched function on every change.
  6. A dashboard shows the progress.

## How one function gets done

1. **Pick:** the next function of the current unit (one original source file; the game had about 1,200), small ones and callees first.
2. **Read:** what Ghidra shows of it (disassembly and pseudo-C, `tools/inventory/dump.ps1`), class names from the game's own type information, and the already-matched functions and struct notes of that unit.
3. **Write** the C++ in `src/decomp/<unit>/`, **compile** it with VS 2003 (`cl` 13.10.3077, `/O2 /G7`), and **compare** (`tools/verify/verify.py`).
4. **If it matches:** record it in `progress/matched.txt`. If not, try again a few times, changing only the source. If it still fails, write down why and move on. Only after several real attempts may a function go to `progress/equivalent.txt`, as CLAUDE.md says.
5. **Every batch** (about 20 functions, or a finished unit): a pull request with a short summary.

Routine functions use a cheaper model (Sonnet); hard ones get the strongest one (CLAUDE.md).

## Checking it on GitHub, without the game's files

GitHub must re-check every matched function on every push (CLAUDE.md), but the game's exe can never be uploaded. The plan:
- For every matched function, `progress/` keeps a **fingerprint**: a hash of its original bytes, with the linker-filled address fields left out, plus where those address fields point.
- GitHub compiles our source with VS 2003 and compares the fingerprints.
- This needs no game file. Hashes and addresses are allowed in the repo (CLAUDE.md).
- This needs the 2003 compiler on GitHub's machines: that is question Q2 (recommended: download it from archive.org and check its hash on every run).

## Technical notes (for future sessions)

- **Inventory:** `progress/inventory.csv`, 67,486 rows (address, size, Ghidra name, origin game/lib/generated, class, subsystem). Totals are in `progress/progress.json`.
- **Units:** the linker kept each source file's functions together, so a unit is a contiguous address range. Boundaries come from class names, string references and the gaps between objects; each unit gets a `unit.json` (see `src/decomp/GameTimer/`).
- **Fingerprint for CI:** per function, the SHA-256 of its bytes with relocation fields zeroed, its size, and the list of (offset, target address). `verify.py` produces it locally from the exe and stores it on `--record`. CI then runs a `--fingerprints` mode against `progress/`. **The verifier is hashed in CI and must not be edited to make a function pass**, so adding this mode is a reviewed change on its own.
- **The loop:** a queue file (next functions per unit), one worker session at a time on this PC, batch PRs per unit. A run that fails or stalls leaves the queue as it was.
- **Since the pilot (2026-10-24):**
  - A scheduled coordinator session runs 3 Sonnet workers in parallel, each on its own group of functions in its own worktree. It merges, checks and records their work into one batch PR a day: [../decomp/coordinator.md](../decomp/coordinator.md), [../decomp/worker-brief.md](../decomp/worker-brief.md).
  - The pilot did 54 matches per one-hour run, for about 4% of the weekly limit.
  - What the workers learned: [../decomp/matching-notes.md](../decomp/matching-notes.md).
