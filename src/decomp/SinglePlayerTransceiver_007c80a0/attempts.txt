# Functions of this unit that are not in unit.json, with the reason. Format: address  reason
007c8100  CSinglePlayerTransceiver destructor (called by the deleting destructor 0x007c80c0 and by Reset 0x007c8390, which both match). The exe's body is only the member clean-up: no vtable-pointer stores at the start. Our compiler always emits them (two stores of the class's vtables plus the vtordisp store) when the destructor is declared; the rest of the body is identical. Tried: declared out of line, declared inline (virtual ~X() {}), implicit destructor (the compiler then makes a different function, `vbase destructor', with the class start as `this`, and inlines it into Reset), __declspec(novtable) (removes the stores but also the ones in the constructor, which the exe's constructor 0x007c78a0 has), /O1 /Os /Ox /Og /Ow /G6 /GX /Od (no change), a matrix of ITransceiver/CObjectBase destructor kinds (inline, extern, pure, none). Other classes of the game have the same shape (0x00718660, 0x00709280, deleting destructor 0x00709430 whose derived vptr store is also missing), so it is a convention of the original source or build, not of this class. The definition stays in SinglePlayerTransceiver.cpp because the compiler only emits the deleting destructor (0x007c80c0) when the destructor is defined in the unit.
007c82b0  CSimpleTempTransceiver destructor: same situation as 0x007c8100 (members: timer pointer, counted pointer, command vector; used by the deleting destructor 0x007c8280 and Reset 0x007c8330, which match).
007c8490  IBinSaver::AddVec (save/load of the command vector). Very close, see drafts.cpp: the only differences are scheduling and register choice. The exe loads the vector pointer after the IsReading() call and hoists `last` and a zero register (xor ebx,ebx) above the test; our compile loads the pointer before or after the test in the wrong order and uses ebx for the address of `last` instead of a zero constant. Tried: local copy first, copy after the call, copy in both branches, `last` in a local, zero as a const local, chained zero stores, a Reset() member.

# What matched, and what it needed (for matching-notes.md)
- /Ob1: the Chunk<T> helper templates are free functions without `inline`; with /Ob2 (the /O2 default) the compiler inlines them, the exe calls them.
- The 5th argument of Chunk<T> (the address of the function's parameter) is a template parameter `X *x` (the callers pass &pf where pf is the incoming IBinSaver* parameter; in AddVec it is the address of the vector parameter).
- In the save methods (operator&) of the three transceivers the exe keeps the saver in esi and `this` in edi. That needs a local copy `IBinSaver *f = pf;` with `&pf` passed to Chunk: if f itself is passed by address, the compiler re-reads it from the stack after every call. (SubA/SubB's methods match without the copy.)
- A class whose destructor and save method override the virtual base's (CObjectBase) gets `this` = the virtual base subobject (offset 0x90, 0x2c, 0x68) and a vtordisp field. A replay transceiver needs a declared virtual destructor, otherwise the vtordisp (4 bytes) is missing and every offset is 4 off.
- `this->X::~X(); a = m_weak; b = m_strong; new (this) X; m_weak += a; m_strong += b;` gives Reset (0x007c8330, 0x007c8390): a direct (qualified) destructor call, and placement new, whose constructor call has the hidden argument 1 and the null test on `this`.
- The deleting destructor calls CObjectBase's own operator delete (0x008790b0), not the global one that the pathfinder units use (0x00879240): give CObjectBase a `static void operator delete(void *)`. CObjectBase's destructor must be inline (`{}`), so that its vptr store (0x00e0a7a0) appears in the deleting destructor.
- The pointer holders' destructors are inline: counted pointer = `if (p) p->Release()`, virtual-base pointer = same through the vbptr, converted pointer = `ToBase(p, p)->Release()`.
