# Functions of this unit that are not in unit.json, with the reason. Format: address  reason
007c8490  IBinSaver::AddVec (save/load of the command vector). Very close, see drafts.cpp: the only differences are scheduling and register choice. The exe loads the vector pointer after the IsReading() call, then `last` (edx) and a zero register (xor ebx,ebx), then `test al,al`. The best draft (local copy v = pv BEFORE the call, `last` in a local) has the exe's length (201 bytes) and the same zero register, hoisted `last` and register stores, but loads the pointer before the call and tests with `cmp al,bl`. Moving the copy after the call loses the zero register (ebx then holds &v->last, `lea ebx,[edi+4]`). Tried (about 40 combinations, a search script over: copy before/after/in both branches/none, `last` local before/in branches/none, 3 stores or a chain, `if (IsReading())` or a bool first, memset, an aggregate zero temp, destroy + placement new, a zero const local, a Reset() member).

# What matched, and what it needed (for matching-notes.md)
- /Ob1: the Chunk<T> helper templates are free functions without `inline`; with /Ob2 (the /O2 default) the compiler inlines them, the exe calls them.
- The 5th argument of Chunk<T> (the address of the function's parameter) is a template parameter `X *x` (the callers pass &pf where pf is the incoming IBinSaver* parameter; in AddVec it is the address of the vector parameter).
- In the save methods (operator&) of the three transceivers the exe keeps the saver in esi and `this` in edi. That needs a local copy `IBinSaver *f = pf;` with `&pf` passed to Chunk: if f itself is passed by address, the compiler re-reads it from the stack after every call. (SubA/SubB's methods match without the copy.)
- A class whose destructor and save method override the virtual base's (CObjectBase) gets `this` = the virtual base subobject (offset 0x90, 0x2c, 0x68) and a vtordisp field. A replay transceiver needs a declared virtual destructor (even undefined), otherwise the vtordisp (4 bytes) is missing and every offset is 4 off.
- DESTRUCTORS WITHOUT VPTR STORES (0x007c8100, 0x007c82b0): a destructor you declare always begins with stores of the class's vtable pointers (and the vtordisp). The exe's have none: they are the compiler's IMPLICIT destructors. Do not declare or define ~X(). Call it as `this->X::~X();` (qualified: an unqualified explicit call is a virtual call). The compiler then emits `??1X@@UAE@XZ` as a function with `this` = the virtual base, member clean-up only, no stores. Other classes of the game (0x00718660, 0x00709280, deleting destructor 0x00709430) are the same shape. To get the vtable and the deleting destructor (`??_G`) emitted the unit must define a constructor (here an empty one; the real constructors 0x007c78a0 / 0x007c7d40 are not reconstructed).
- The timer pointer's class has its own vtable pointer at +0 and the vbptr at +4: give it a virtual function of its own, not only overrides of the virtual base's.
- `this->X::~X(); a = m_weak; b = m_strong; new (this) X; m_weak += a; m_strong += b;` gives Reset (0x007c8330, 0x007c8390): a direct (qualified) destructor call, and placement new, whose constructor call has the hidden argument 1 and the null test on `this`.
- The deleting destructor calls CObjectBase's own operator delete (0x008790b0), not the global one that the pathfinder units use (0x00879240): give CObjectBase a `static void operator delete(void *)`. CObjectBase's destructor must be inline (`{}`), so that its vptr store (0x00e0a7a0) appears in the deleting destructor.
- The pointer holders' destructors are inline: counted pointer = `if (p) p->Release()`, virtual-base pointer = same through the vbptr, converted pointer = `ToBase(p, p)->Release()`.
