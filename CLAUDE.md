# open-homm5: project rules

Read this file at the start of every session. It overrides your defaults for this repo.

## Goal

Make Heroes of Might and Magic V: Tribes of the East (with the MMH5.5 mod) better for a small group of friends:

1. **First:** fast, stable AI turns in co-op games (3+ humans vs AI over GameRanger).
2. **Then:** a smarter AI, then built-in online play without GameRanger.
3. **Long term:** a full decompilation that becomes an open Heroes V engine (like VCMI for Heroes III).

The repo is public, but it is built for us. Others are welcome to use it.

Full plan (owner's doc): https://claude.ai/code/artifact/2e552544-25e8-4c39-84af-611c4866f400

## The owner

- Beginner in reverse engineering and C/C++. Explain decisions in plain language.
- Supervises a few times a day; you do most of the engineering.
- Plays and tests on a Windows PC and a Linux PC (Wine/Proton). Steam copy of the game.
- Must approve: downloads/installs, anything touching the game folder, publishing, spending money.

## Paths

- Game install (read only, never modify): `C:\Program Files (x86)\Steam\steamapps\common\Heroes of Might and Magic 5 Tribes of the East`
  - `bin\` holds the exes (vanilla `H5_Game.exe`, MMH5.5's `MMH55*.exe` variants).
  - Warning: the GameRanger setup guide tells players to rename `H5_Game.exe` and replace it with an MMH5.5 exe. Verify which file is the real vanilla exe (by hash and version info) before treating anything as the reference.
- Reference copies of binaries: `ref/` inside the repo, **gitignored**. Copy, never move.

## Hard rules

- **Never commit game files**: no exes, DLLs, `.pak`, data, maps, saves, or Ghidra/IDA databases. Hashes and our own notes are fine.
- **Never modify the game folder.** For testing, the owner sets up a separate copy of the game.
- Byte-matching is the definition of "done" for a decompiled function (see Oracle). Readable but unverified code is a draft.
- Forbidden in decompiled source: inline assembly, naked functions, embedded bytes, object patching, `#pragma` tricks aimed at the checker.
- Never edit `tools/verify/` to make a function pass. CI hashes the verifier; a changed hash fails the build.
- Do not "improve" original behavior inside decomp files. Keep original bugs. Improvements live in `src/mods/`, clearly separated.
- Do not restructure the original architecture (no swapping globals for hash tables, etc.).
- If a rule blocks you, stop and write the question in `docs/questions.md` instead of working around it.

## Architecture: two tracks, one codebase

1. **Decomp track:** reconstruct the vanilla ToE 3.1 exe function by function into C++ under `src/decomp/`, grouped by original source file (translation unit). Verified by the oracle.
2. **Hook track:** `src/hook/` builds a DLL loaded by the game (proxy DLL or loader). It swaps original functions for our versions (decompiled or modded) at runtime, so improvements ship before the decomp is complete.

Option A is the chosen co-op design: **host-authoritative AI**. Only the host computes AI turns and broadcasts the resulting actions; clients apply them. Option B (deterministic AI on every client) is the fallback.

## Oracle (definition of correct)

- Compile each reconstructed function with the **same MSVC version** that built the original (identify it from the PE Rich header).
- Compare the function's bytes in our `.obj` against the original exe. Exclude relocation bytes, but check that each relocation targets the same symbol and offset.
- Record matched functions in `progress/matched.txt` (address, name, TU). CI re-verifies every recorded function on each push and fails on regressions.
- Functions that cannot match (compiler nondeterminism, linker folding) go to `progress/equivalent.txt` with a written reason, only after several genuine attempts.

## Workflow

- One GitHub issue per translation unit; labels for subsystem (ai, net, adventure, combat, ui, render, io, lib).
- Work on one function at a time. Finish it (match or documented give-up) before starting another.
- Small branches, one PR per batch, each with a short plain-language summary: what changed, how it was verified, how the owner can test it.
- Keep notes in `docs/` (subsystem maps, struct layouts, findings). Notes are for future sessions too: write them as if for a newcomer.
- Use Sonnet for routine functions; reserve Opus for hard ones. Usage comes from the owner's Max plan, shared with chat.

## Phases (gates in brackets)

0. Setup: repo, tools, inventory, DLL loads into the game [DLL loads and logs AI turns; game runs normally]
1. Investigate: map AI turn and network code; game-state hashing [first divergence pinned in a 2-client test]
2. Prototype: host runs the fast AI and sends its moves [2 clients, fast AI, 20 turns, no desync]
3. Harden: 3+ humans on GameRanger, Wine on Linux [3+ humans finish a game, no crash]
4. Release: v0.1 on GitHub [install guide, first outside tester]
5. Smarter AI on the host [beats the old AI on AI-vs-AI test maps]
6. Built-in online play (GameNetworkingSockets + small lobby) [join a friend's game from inside the game]
